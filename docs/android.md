# Android prototype

This is a **local-first** Android prototype, separate from the Windows desktop
interface. The mobile editor uses Milkdown to display and edit the same `.md`
files with headings, lists, emphasis, links, tables, code and inline images.
Since 0.4.5, an optional WebDAV client can synchronize Markdown and image assets
with the Windows app. WebDAV remains **off by default** until an account is
configured. This feature requires on-device validation before relying on it
for important notes.

## Build and try

Install Android Studio, Android SDK/NDK and Rust Android targets as described in
the [Tauri Android prerequisites](https://v2.tauri.app/start/prerequisites/).
Then, from the repository root:

```sh
npm ci
npm run android:init
npm run android:build
```

The last command builds an optimized **Release** APK for `aarch64` devices.
Release APKs are **unsigned by default** and cannot be installed directly.
Find the raw APK under `src-tauri/gen/android/app/build/outputs/apk/`.
The Android GitHub Actions job signs a test copy, verifies its signature and
uploads `minipad-next-arm64-test.apk` as its own artifact (not zipped, so the
download is the `.apk`). The job summary says which key signed it. For local
development, use `npm run tauri -- android dev`.

### Signing key

- **With the four repository secrets set** (below), CI signs with your stable key.
  Every build then has the same signature, so a newer test APK installs **over**
  an older one and keeps its notes.
- **Without them**, CI signs with a throw-away key generated on each run. Such an
  APK installs fine, but a later build cannot be installed over it (uninstall
  first, which removes the app-private notes).

Either way: **do not keep important notes in this prototype** until data
import/export exists. None of these keys is a Play Store publishing key.

Create the key once, on your own computer (any JDK or Android Studio's `keytool`),
and keep the file and its passwords somewhere safe. Losing it means a new key and
one uninstall; never commit it:

```sh
keytool -genkeypair -keystore minipad-release.jks -storetype PKCS12 \
  -alias minipad -keyalg RSA -keysize 2048 -validity 10000
```

Then add these **repository secrets** (GitHub: Settings → Secrets and variables →
Actions). Set all four or none; a partial set fails the signing step on purpose.

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | the `.jks` file as one base64 string |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password |
| `ANDROID_KEY_ALIAS` | the alias (`minipad` above) |
| `ANDROID_KEY_PASSWORD` | the key password (the same as the keystore password for PKCS12) |

To produce the base64 value (copy it into the secret; it is not a file to upload):

```sh
# Linux
base64 -w0 minipad-release.jks
# macOS (its base64 has no -w option)
base64 -i minipad-release.jks | tr -d '\n'
# Windows PowerShell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("minipad-release.jks"))
```

Pull requests from forks never see the secrets, so their builds use the throw-away key.

The Android-only `build.frontendDist` embeds five files from
`mobile-dist/`: `mobile.html`, `mobile.css`, the bundled `js/mobile.js`, and the
desktop editor's `style.css` and `vendor/highlight.js` (copied as
`desktop-editor.css` and `vendor/highlight.js`). The editor itself (`src/js/editor.js`
and what it imports) is bundled into `js/mobile.js`, so changes under `src/js/`
(except the desktop-only `main.js`, `ball.js`, `search.js` and `trash.js`),
`src/style.css` and the scripts that prepare the vendor files also reach the APK. The desktop window
UI is not included, and the Windows build continues to use `src/`. The directory
is generated by `npm run prepare-mobile` and must not be checked into Git.

There is intentionally no Play Store release or automatic publication in
this PR. On pull requests the Android job runs only when a file the APK is made
from changes (`pull_request.paths` in `.github/workflows/android.yml`, which
excludes the desktop-only Rust modules and scripts). `tests/android-paths.test.mjs`
(part of `npm run test:mobile`) bundles the mobile frontend and reads the Android
modules from `lib.rs` to check that list both ways, and names the line to add when
a new file is missing. Manual runs and release builds are not filtered.

## Current scope

- Choose notebooks and pages with touch-sized selectors; switch between Milkdown
  reading and editing modes and format content with a horizontally scrollable
  touch toolbar.
- Edit headings, emphasis, links, lists, quotations and inline code. Fold blocks,
  titled code blocks and styled spans use the same shared editor as Windows.
  A note containing any other raw HTML tag (outside code blocks and inline code)
  opens as raw Markdown instead, so nothing is stripped by mistake.
- Insert images from the Android file picker or paste images from a compatible
  clipboard. Files are restricted to PNG/JPG/GIF/WebP/BMP and 10 MiB, saved in
  the current notebook's `assets/` directory and referenced by relative paths
  in Markdown, consistent with Windows.
- Light/dark follows the system setting (menus and bars included). The format toolbar
  stays above the soft keyboard, and selecting text shows a floating format bar below
  the selection (the system's own copy/paste popup uses the space above).
- Add notebooks and pages; their names, and every confirmation, use the in-app
  dialog (see below), never the system `prompt()` / `confirm()`.
- Store notes in the Android app-private data directory under `notes/`. Switching
  pages lists names only and reads just the opened page. Images in a notebook's
  `assets/` are loaded by the WebView from `http://note.localhost/img?book=…&path=…`,
  the same `note` protocol the Windows app uses, so they never travel over IPC as
  base64. A failed autosave is retried a few times before it waits for the next edit.
- Preserve the desktop `.md` and notebook directory layout. Saving uses the
  shared Rust collision-safe note writer and keeps conflict copies when its
  expected file version differs.
- The desktop entry point and Windows installer are unchanged.

**No background service or Play Store integration; background transitions can
trigger one foreground WebDAV sync when the WebView is still running.
There is no Android note import/export, image cropping, or desktop-only floating UI.** A browser-based Android-shell test covers editing, saving,
read-only mode, and attachment insertion, but it cannot substitute for actual
Android devices. In particular, file pickers and Chinese IMEs need on-device
testing. Android-private app storage can be removed by uninstalling the APK,
so treat this stage as a test build and avoid storing important notes.

## Links, dialogs and the Back key (0.4.5)

- **Links:** with the page not editable (reading mode or a read-only page), tapping
  a link opens it: web pages in the system browser, or in the in-app browser
  (Custom Tabs) when **外观设置 → 链接** says so; `mailto:` and `tel:` go to the
  matching app. Other links (relative paths and so on) only show a notice. While
  editing, a tap just places the caret unless **编辑时点链接也直接打开** is on;
  Ctrl+tap with a hardware keyboard always opens. The page never navigates away:
  `mobile_open_url` accepts `http`, `https`, `mailto` and `tel` only, and a
  navigation guard cancels anything that would leave `tauri.localhost`.
- **Dialogs:** naming pages and notebooks and all confirmations use the shared
  `#dialog` with Chinese buttons. The name field takes the focus (the keyboard
  comes up), Enter confirms, Cancel or a tap outside cancels, and the dialog stays
  above the soft keyboard in every interface style.
- **Back key:** closes the top open layer, one per press: dialog, menus and format
  popups, find panel, sync settings, appearance settings, drawer. The page only
  listens for Back while something is open, so with nothing open Back sends the
  app to the background as usual.
- **Format bar:** 链接 asks for the address in the dialog, 任务 turns the paragraph
  into a task or toggles it, and the buttons and order chosen under 自定义 are kept
  on this phone.

## WebDAV synchronization (0.4.5)

1. Open the notebook drawer and select **同步设置**.
2. Enter a WebDAV server URL, username, and app-specific password. For Jianguoyun
   use its third-party application password. The remote folder defaults to
   `/MinipadNext/`. Use HTTPS; HTTP requires explicit opt-in for a trusted LAN.
3. Choose **合并** for the first sync unless you specifically need the server or
   phone as the authoritative copy. **以网盘为准** and **以手机为准** may move
   extra files to the corresponding trash; a high deletion count requires confirmation.
4. Run **测试连接** (it tests what is typed in the form and saves nothing), then
   enable synchronization and save the settings. Use the drawer's
   **立即同步** button when you need an immediate transfer.
5. Automatic triggers are available for opening/returning to the app, successful
   saves, a foreground timer, and switching to the background. Android does
   not run a permanent background sync service.

A WebDAV account's password stays in the Android app-private data folder,
outside the synchronized `notes/` tree, in its `no_backup` folder so Android's
automatic backup does not copy it. The server URL and account options
remain on the current device. The file format is unchanged: ordinary `.md`
files and `assets/` images. Conflicts are kept as separate files by default.
Offline editing and normal local autosave continue without a server connection.
Check the in-app sync status and error history for problems.

**Warning:** An uninstalled APK removes app-private data. Keep a second backup
until the Windows and Android workflow passes real-device testing. A successful
mock/browser test cannot verify phone storage and network behavior.

## Planned follow-ups

The touch interface, Milkdown editor and image import were added **within PR #38**
to keep the Android work together, as requested. Future milestones:

1. **Sync hardening:** validate deletion protection, conflicts, offline behavior,
   certificate errors and compatibility with different WebDAV providers.
2. **Device validation:** Chinese input methods, keyboards, external file-picker
   compatibility and image rendering on actual devices, plus the 0.4.5 links,
   in-app dialogs and Back key on a real phone.

WebDAV work must not treat HTTP/network failure as a deletion or overwrite local
unsaved changes. A sync implementation is not complete until that can be
demonstrated by tests.
