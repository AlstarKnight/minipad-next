# Android prototype

This is a **local-first** Android prototype, separate from the Windows desktop
interface. The mobile editor uses Milkdown to display and edit the same `.md`
files with headings, lists, emphasis, links, tables, code and inline images.
There is no WebDAV yet; **this APK does not sync notes between devices**.

## Build and try

Install Android Studio, Android SDK/NDK and Rust Android targets as described in
the [Tauri Android prerequisites](https://v2.tauri.app/start/prerequisites/).
Then, from the repository root:

```sh
npm ci
npm run android:init
npm run android:build
```

The last command builds an optimized **Release** APK for `aarch64` devices.
Release APKs are **unsigned by default** and cannot be installed directly.
Find the raw APK under `src-tauri/gen/android/app/build/outputs/apk/`.
The Android GitHub Actions job signs a test copy, verifies its signature and
uploads `minipad-next-arm64-test.apk` as its own artifact (not zipped, so the
download is the `.apk`). The job summary says which key signed it. For local
development, use `npm run tauri -- android dev`.

### Signing key

- **With the four repository secrets set** (below), CI signs with your stable key.
  Every build then has the same signature, so a newer test APK installs **over**
  an older one and keeps its notes.
- **Without them**, CI signs with a throw-away key generated on each run. Such an
  APK installs fine, but a later build cannot be installed over it (uninstall
  first, which removes the app-private notes).

Either way: **do not keep important notes in this prototype** until data
import/export exists. None of these keys is a Play Store publishing key.

Create the key once, on your own computer (any JDK or Android Studio's `keytool`),
and keep the file and its passwords somewhere safe. Losing it means a new key and
one uninstall; never commit it:

```sh
keytool -genkeypair -keystore minipad-release.jks -storetype PKCS12 \
  -alias minipad -keyalg RSA -keysize 2048 -validity 10000
```

Then add these **repository secrets** (GitHub: Settings → Secrets and variables →
Actions). Set all four or none; a partial set fails the signing step on purpose.

| Secret | Value |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | the `.jks` file as one base64 string |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore password |
| `ANDROID_KEY_ALIAS` | the alias (`minipad` above) |
| `ANDROID_KEY_PASSWORD` | the key password (the same as the keystore password for PKCS12) |

To produce the base64 value (copy it into the secret; it is not a file to upload):

```sh
# Linux
base64 -w0 minipad-release.jks
# macOS (its base64 has no -w option)
base64 -i minipad-release.jks | tr -d '\n'
# Windows PowerShell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("minipad-release.jks"))
```

Pull requests from forks never see the secrets, so their builds use the throw-away key.

The Android-only `build.frontendDist` embeds five files from
`mobile-dist/`: `mobile.html`, `mobile.css`, the bundled `js/mobile.js`, and the
desktop editor's `style.css` and `vendor/highlight.js` (copied as
`desktop-editor.css` and `vendor/highlight.js`). The editor itself (`src/js/editor.js`
and what it imports) is bundled into `js/mobile.js`, so desktop changes under
`src/js/`, `src/style.css` and `scripts/` (which prepares the vendor files) also reach the APK. The desktop window
UI is not included, and the Windows build continues to use `src/`. The directory
is generated by `npm run prepare-mobile` and must not be checked into Git.

There is intentionally no Play Store release or automatic publication in
this PR. GitHub Actions runs the Android job only for relevant PRs or manual
dispatch.

## Current scope

- Choose notebooks and pages with touch-sized selectors; switch between Milkdown
  reading and editing modes and format content with a horizontally scrollable
  touch toolbar.
- Edit headings, emphasis, links, lists, quotations and inline code. Fold blocks,
  titled code blocks and styled spans use the same shared editor as Windows.
  A note containing any other raw HTML tag (outside code blocks and inline code)
  opens as raw Markdown instead, so nothing is stripped by mistake.
- Insert images from the Android file picker or paste images from a compatible
  clipboard. Files are restricted to PNG/JPG/GIF/WebP/BMP and 10 MiB, saved in
  the current notebook's `assets/` directory and referenced by relative paths
  in Markdown, consistent with Windows.
- Light/dark follows the system setting (menus and bars included). The format toolbar
  stays above the soft keyboard, and selecting text shows a floating format bar below
  the selection (the system's own copy/paste popup uses the space above).
- Add notebooks and pages without any desktop-only window commands.
- Store notes in the Android app-private data directory under `notes/`. Switching
  pages lists names only and reads just the opened page; decoded images are cached
  in memory. A failed autosave is retried a few times before it waits for the next edit.
- Preserve the desktop `.md` and notebook directory layout. Saving uses the
  shared Rust collision-safe note writer and keeps conflict copies when its
  expected file version differs.
- The desktop entry point and Windows installer are unchanged.

**No WebDAV, note import/export, background sync, image cropping, or desktop-only
floating UI.** A browser-based Android-shell test covers editing, saving,
read-only mode, and attachment insertion, but it cannot substitute for actual
Android devices. In particular, file pickers and Chinese IMEs need on-device
testing. Android-private app storage can be removed by uninstalling the APK,
so treat this stage as a test build and avoid storing important notes.

## Planned follow-ups

The touch interface, Milkdown editor and image import were added **within PR #38**
to keep the Android work together, as requested. Future milestones:

1. **WebDAV foundation:** settings, credential storage, remote list/download/upload,
   ETag checking and manual foreground sync shared with Windows.
2. **Sync hardening:** tombstones/deletions, conflicts, retry/offline behavior,
   compatibility testing with different WebDAV servers and stable Android update
   signing.
3. **Device validation:** Chinese input methods, keyboards, system back navigation,
   external file-picker compatibility and image rendering on actual devices. Also
   confirm that links open (`window.open`; no opener plugin is bundled on Android)
   and that the `prompt()` dialogs for new notebooks and pages appear.

WebDAV work must not treat HTTP/network failure as a deletion or overwrite local
unsaved changes. A sync implementation is not complete until that can be
demonstrated by tests.
